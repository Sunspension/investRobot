## 🔧 **Технические требования**

### Параметры функций
- ✅ **Сворачивать параметры если больше 2-х**
- ✅ **Использовать dataclasses для группировки**
- ✅ **Длинные сигнатуры функций разбивать на несколько строк**
- ✅ **Каждый параметр на отдельной строке с правильным отступом**
- ✅ **Особенно важно для методов __init__, __aexit__ и функций с 3+ параметрами**

### Тестирование
- ✅ **Создавать моки для всех внешних зависимостей**
- ✅ **Использовать интерфейсы для полиморфизма**

## 📝 **Стиль кода**

### Именование
- ✅ **Понятные имена переменных и функций**
- ✅ **Документация для сложных методов**
- ✅ **Следовать конвенциям Apple для интерфейсов**

### Конвенции именования интерфейсов (Apple Style)
- ✅ **Использовать семантические суффиксы вместо префиксов**
- ✅ **Суффикс `-able` для интерфейсов возможностей**
- ✅ **Суффикс `-ing` для интерфейсов процессов**
- ✅ **Суффикс `-er` для интерфейсов исполнителей**

#### Примеры правильного именования:
```python
# ✅ Хорошо - Apple Style
class SessionStatsable(ABC):           # может предоставлять статистику
class SessionInitializable(ABC):       # может инициализироваться  
class SessionControllable(ABC):        # может управляться
class TradingSessionable(ABC):         # может торговать
class DependenciesProvidable(ABC):     # может предоставлять зависимости
class DependenciesProviderFactoryable(ABC):  # может создавать фабрики

# ❌ Плохо - старый стиль с префиксами
class ISessionStats(ABC):              # префикс I
class SessionInterface(ABC):           # суффикс Interface
class DependenciesProviderInterface(ABC):  # суффикс Interface
```

#### Принципы Apple Style:
1. **Семантичность** - имя должно описывать способность/функцию
2. **Читаемость** - `SessionStatsable` читается как "может предоставлять статистику сессии"
3. **Единообразие** - все интерфейсы следуют одной конвенции
4. **Естественность** - звучит естественно в контексте использования

### Форматирование сигнатур функций
```python
# ❌ Плохо - все в одну строку
def __init__(self, config: TradingConfig, dependencies: TradingDependencies, force_start: bool = False):

# ✅ Хорошо - каждый параметр на отдельной строке
def __init__(
    self, 
    config: TradingConfig, 
    dependencies: TradingDependencies, 
    force_start: bool = False
):
```

### Обработка ошибок
- ✅ **Логировать ошибки с контекстом**
- ✅ **Не игнорировать исключения**

## 📚 **Создание документации и тестирование**

### Процесс создания документации
1. **Обсуждение**: Всегда обсуждать необходимость демо/документации
2. **Выбор формата**: Предпочитать документацию с примерами вместо демо
3. **Структура**: Документация должна включать:
   - Обзор и преимущества
   - Практические примеры кода
   - Объяснение концепций
   - Ссылки на связанные материалы
4. **Размещение**: Документация в `docs/`, примеры в `examples/`

### Что считается демо, а что тестированием
- **Демо файлы** ❌ - файлы, созданные для демонстрации без реальной пользы
- **Тестовые файлы** ✅ - файлы для проверки работоспособности с моками
- **Моки в тестах** ✅ - необходимы для изоляции тестируемого кода
- **Моки в демо** ❌ - не нужны, лучше показать реальную работу

### Принципы создания файлов
- **Один файл - одна цель** - не создавать файлы "на всякий случай"
- **Обсуждать перед созданием** - всегда спрашивать, нужен ли файл
- **Предпочитать документацию** - лучше объяснить, чем показать

# Строгие правила проекта investRobot

## 🚨 КРИТИЧЕСКИ ВАЖНО - ВСЕГДА СОБЛЮДАТЬ!

### 1. ИНКАПСУЛЯЦИЯ И ПРИНЦИПЫ SOLID

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не использовать `hasattr()` для проверки собственных атрибутов
- **НИКОГДА** не обращаться к приватным атрибутам (начинающимся с `_`) извне класса
- **НИКОГДА** не создавать зависимости внутри класса
- **НИКОГДА** не делать внутренние атрибуты публичными

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** использовать публичные методы и свойства для доступа к данным
- **ВСЕГДА** делать внутренние атрибуты приватными (`_attribute`)
- **ВСЕГДА** создавать явные методы для проверки состояния объектов
- **ВСЕГДА** использовать интерфейсы для доступа к данным
- **ВСЕГДА** использовать типизацию для избежания `hasattr()`

### 2. ИМПОРТЫ

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не делать импорты внутри функций или методов
- **НИКОГДА** не делать импорты внутри классов (кроме исключений)
- **НИКОГДА** не оставлять неиспользуемые импорты

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** размещать все импорты в начале файла
- **ВСЕГДА** группировать импорты: стандартная библиотека, сторонние, локальные
- **ВСЕГДА** удалять неиспользуемые импорты
- **ВСЕГДА** использовать абсолютные импорты

### 3. DEPENDENCY INJECTION

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** передавать зависимости через конструктор
- **ВСЕГДА** использовать интерфейсы для зависимостей
- **ВСЕГДА** создавать зависимости в фабриках
- **ВСЕГДА** инжектировать все внешние зависимости

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не создавать зависимости внутри класса
- **НИКОГДА** не использовать `new` или прямые вызовы конструкторов

### 4. ПУБЛИЧНЫЕ СВОЙСТВА И API

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** минимизировать публичный API
- **ВСЕГДА** оставлять только необходимые публичные методы/свойства
- **ВСЕГДА** использовать `@property` для контролируемого доступа
- **ВСЕГДА** делать свойства read-only где возможно

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не создавать публичные свойства для внутренних деталей
- **НИКОГДА** не экспонировать больше, чем необходимо

### 5. СТИЛЬ КОДА И СТАНДАРТЫ

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** использовать Apple Style для интерфейсов
- **ВСЕГДА** разбивать длинные сигнатуры функций на несколько строк
- **ВСЕГДА** размещать импорты в начале файла
- **ВСЕГДА** использовать `get_logger(__name__)` для логирования
- **ВСЕГДА** удалять неиспользуемые импорты

### 6. ТЕСТИРОВАНИЕ

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** исправлять падающие тесты вместо их удаления
- **ВСЕГДА** использовать моки для внешних зависимостей
- **ВСЕГДА** размещать моки в отдельных файлах в папке `mocks/`
- **ВСЕГДА** запускать тесты после изменений
- **ВСЕГДА** анализировать причину падения перед действиями
- **ВСЕГДА** исправлять код, если считаем тест верным
- **ВСЕГДА** исправлять тест, если намеренно изменили логику
- **ВСЕГДА** удалять тест, только если он стал неактуальным

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не оставлять падающие тесты
- **НИКОГДА** не создавать моки внутри методов
- **НИКОГДА** не игнорировать сломанные тесты
- **НИКОГДА** не использовать базу данных в тестах

### 7. БАЗА ДАННЫХ В ТЕСТАХ

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не подключаться к реальной базе данных в тестах
- **НИКОГДА** не использовать SQLite файлы в тестах
- **НИКОГДА** не создавать временные базы данных для тестов
- **НИКОГДА** не использовать `db_path`, `market.db`, `candles.db` в тестах

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** использовать моки для данных из базы
- **ВСЕГДА** создавать тестовые данные в памяти
- **ВСЕГДА** использовать `Mock` объекты для API базы данных
- **ВСЕГДА** тестировать логику без внешних зависимостей

### 8. МОКИ ДЛЯ ЗАВИСИМОСТЕЙ В ТЕСТАХ

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не использовать реальные зависимости в тестах
- **НИКОГДА** не создавать реальные объекты API клиентов
- **НИКОГДА** не подключаться к внешним сервисам в тестах
- **НИКОГДА** не использовать реальные базы данных, файлы, сети

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** использовать `Mock`, `AsyncMock`, `MagicMock` для всех зависимостей
- **ВСЕГДА** мокать все внешние API вызовы
- **ВСЕГДА** создавать тестовые данные в памяти
- **ВСЕГДА** изолировать тестируемый объект от внешнего мира

### 7. ДОКУМЕНТАЦИЯ И ДЕМО

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** создавать документацию с примерами использования
- **ВСЕГДА** спрашивать подтверждение перед созданием документации
- **ВСЕГДА** обновлять документацию при изменениях

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не создавать демо файлы с мок данными
- **НИКОГДА** не создавать примеры без запроса

### 8. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ

#### ✅ ОБЯЗАТЕЛЬНО:
- **ВСЕГДА** следовать принципам SOLID
- **ВСЕГДА** использовать Dependency Injection
- **ВСЕГДА** создавать интерфейсы для всех зависимостей
- **ВСЕГДА** разделять ответственности между классами

#### ❌ СТРОГО ЗАПРЕЩЕНО:
- **НИКОГДА** не создавать антипаттерны (дублирование кода, смешивание ответственностей)
- **НИКОГДА** не нарушать принципы инкапсуляции

## 📝 ПРИМЕРЫ ПРАВИЛЬНОГО КОДА:

### ✅ Правильная инкапсуляция:
```python
class MyClass:
    def __init__(self, dependency: Interface):
        self._private_attr = value
        self._dependency = dependency
    
    @property
    def public_data(self) -> str:
        return self._private_attr
    
    def public_method(self) -> bool:
        return self._dependency.is_ready()
```

### ❌ Неправильная инкапсуляция:
```python
class MyClass:
    def __init__(self):
        self.public_attr = value  # ❌ Публичный атрибут
        self._dependency = SomeClass()  # ❌ Создание зависимости внутри
    
    def method(self, obj):
        if hasattr(obj, 'attr'):  # ❌ hasattr для собственных атрибутов
            return obj.attr
```
